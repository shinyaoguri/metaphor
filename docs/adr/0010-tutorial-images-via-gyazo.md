# ADR-0010: チュートリアルの画像も Gyazo の外部 URL で参照する（リポジトリに置くのをやめる）

- **Status**: Accepted
- **Date**: 2026-08-14
- **Deciders**: @shinyaoguri
- **PR / Commit**: (この ADR を含む PR)

## Context

`docs/tutorial/` は 65 点の画像（静止画 PNG 54 点 + 動きの証跡のアニメーション WebP 11 点、
計 3.75 MiB）をリポジトリに置いている。[ADR-0008](0008-docc-reference-images-via-gyazo.md) は
DocC リファレンスの画像を Gyazo へ移したが、チュートリアルは「[#511](https://github.com/shinyaoguri/metaphor/issues/511) のまま
（リポジトリ内・アニメーション WebP）で変更しない」と明示的にスコープ外にしていた。本 ADR は
その判断を更新する。

いま動かす理由は容量そのものではない。3.75 MiB は pack（約 30 MiB）の 12.5% で、まだ誤差の
範囲にある。効くのは**増え方**のほうで、

- 縦糸（第 1〜10 部）は完結したが、横糸（[#550](https://github.com/shinyaoguri/metaphor/issues/550) の部末ミニプロジェクト節など）で節は増え続ける
- 画像は Probe から**再生成できる**。つまり API の描画を直せば 65 点が一斉に撮り直しになる。
  GPU の出力はビット単位で再現しないので、撮り直せば中身が同じでも必ず新しい blob になる

という構造上、「1 回の描画修正 = 数 MiB の恒久的な増加」が今後も繰り返される。history は
書き換えない方針なので、増えたぶんは永久に残る。判断を先送りするほど、移行時に外部化できる
のは新しい画像だけになり、リポジトリに残る死蔵バイトが増える。

#511 が Gyazo を退けた理由のうち、**「版と画像の対応が取れない」は #511 自身がのちに撤回して
いる**（Gyazo の URL は不変・追記型で、本文に URL を書けばその URL は本文と同じコミットに
固定される＝むしろコンテンツアドレスに近い）。残っていた実務上の反論は「Astro のビルド時
最適化が効かなくなり配信サイズがむしろ増える」「再生成パイプラインと噛み合わない」の 2 つで、
どちらも本 ADR で解消できることが実測で分かった（後述）。

### 実測して分かったこと

Gyazo のヘルプは対応形式を jpg / png / gif / mp4（Pro / Teams のみ）と書いており、WebP の
記載が無い。ADR-0008 は DocC が WebP を扱えないためこの点を検証する必要が無かったが、
チュートリアルの動きの証跡はアニメーション WebP なので、ここが移行の成否を決める。実際に
上げて確かめた:

| 確かめたこと | 結果 |
|---|---|
| アニメーション WebP のアップロード | **通る**（`type: "webp"` が返り、`i.gyazo.com/<hash>.webp` で配信される） |
| 配信されるバイト列 | **アップロードしたものと同一**（sha256 一致。再エンコードされない） |
| アニメーションの保持 | **保たれる**（48 フレームの WebP が 48 フレームのまま） |
| サイズ上限 | 35 MB の GIF も通り、同一バイト列で配信された |
| Cache-Control | `public, max-age=31536000`（1 年）。不変 URL の前提と揃っている |

そのうえで、Astro（7.1.6）が `image.remotePatterns` に許可したホストの画像を
**ビルド時に取得して sharp で最適化し、`dist/_astro/` へローカル配置する**ことを、実際に
Gyazo の URL を本文に置いてビルドして確かめた。アニメーションは潰れない
（sharp を `pages: -1` で開くため）。出力 HTML に `i.gyazo.com` は 1 つも残らない。

- Gyazo 上のアニメーション WebP（48 フレーム）→ 出力もアニメーション WebP・48 フレーム
- Gyazo 上のアニメーション GIF（39 フレーム・1.9 MB）→ アニメーション WebP・507 KB へ変換

つまり **#511 が挙げた「配信品質を壊す」は起きない**。読者が受け取るものは今と同じで、
変わるのは実体の置き場だけになる。

## Considered Options

### Option A: 現状維持（リポジトリに置き続ける）
- Pros: いま何もしなくてよい。fork や外部コントリビュータが PR で画像を差し替えられる。
  オフラインでも本文が完結する。リンク切れが原理的に起きない。
- Cons: 描画を直すたびに数 MiB が恒久的に積み上がる。history を書き換えない方針なので
  減らす手段が事実上無い。

### Option B: 画像を Gyazo へ置き、Git では本文と台帳（URL + content hash）だけを管理する
- Pros: リポジトリの増え方が止まる。読者の受け取るものは変わらない（Astro が取得して
  最適化・ローカル配置する）。GitHub 上でも camo 経由でそのまま表示される。既に運用中の
  Gyazo 導線（ADR-0008 / `gyazo-capture` スキル）をそのまま使える。翻訳（[#548](https://github.com/shinyaoguri/metaphor/issues/548)）が
  相対パスの階層問題を持たずに同じアセットを共有できる。
- Cons: リンク切れが無言（別に見張りが要る）。個人アカウント依存で fork から差し替えられない。
  棚卸しにはリポジトリ側に台帳が要る。オフラインでは本文の画像が出ない。

### Option C: `metaphor-assets` のような GitHub 内の別リポジトリ + Pages
- Pros: 全形式を扱える。git で棚卸し・逆引きができる。fork でも辿れる。#511 が
  「将来サイズが逼迫したときの第一候補」としていた案。
- Cons: 運用するリポジトリが 1 つ増え、2 リポジトリ間の同期という新しい失敗経路ができる
  （metaphor ⇄ metaphor-cli の契約で既に 1 つ抱えている）。Gyazo と違って「撮って上げる」が
  1 コマンドで終わらない。得られるものは Option B と同じ「実体を外に出す」で、
  差は棚卸しのしやすさに集約される — そしてそれは台帳で埋められる。

### Option D: 履歴ごと書き換える（git filter-repo）
- Pros: 既存の pack が実際に縮む。
- Cons: 全クローン・fork・過去 PR の参照が壊れ、ルールセット（直接 push 不可）の一時解除も
  要る。tutorial 分は pack の 12.5% しかなく、得られるものが釣り合わない。

## Decision

**Option B を採る。** 画像の実体は Gyazo に置き、Git で管理するのは本文と台帳
（`docs/tutorial/images/manifest.json` の `url` + `sha256`）だけにする。既存の 65 点は
**撮り直さずそのまま上げて**移す（GPU の出力は再現しないので、撮り直すと中身の変わらない
差分が全点に出る）。

決め手は 2 つ。ひとつは、#511 が Gyazo を退けた実務上の理由（配信品質の劣化・パイプラインとの
不整合）が、`image.remotePatterns` と台帳ベースの本文書き換えで**そのまま解消できると実測で
確かめられた**こと。もうひとつは、Option C との差が「棚卸しのしやすさ」だけで、そこは
リポジトリ側の台帳（どの節がどの URL を指すかを Git で追える）で埋まること — その台帳は
ADR-0008 が Follow-up として積み残していたものでもある。

アセットは**不変・追記型**として扱う。撮り直しは既存 URL の差し替えではなく新規アップロード
とし、本文と台帳の URL を更新する。古い URL は消さない。これで「各リビジョンがどの不変
アセットを参照していたか」が Git の履歴そのものになり、過去のリビジョンを checkout すれば
当時の絵が出る。

## Consequences

### Positive
- チュートリアル画像によるリポジトリの増加が止まる。以後の撮り直しは本文と台帳の
  数行の差分だけになる（いまは 1 節あたり数百 KB の新しい blob）。
- 読者が受け取るものは変わらない。website は Astro が最適化した `dist/_astro/*.webp` を
  配信し、GitHub 上の本文は camo 経由で表示される（アニメーションも保たれる）。
- 台帳が「どの節がどの URL を指すか」の正本になり、ADR-0008 が Follow-up にしていた
  URL 台帳・リンク切れ検出・アップロードの自動化がまとめて片付く。DocC 側（#531）も
  同じ仕組みに乗せられる。
- 翻訳（#548）が階層の違う相対パスを持たずに同じアセットを共有できる。
- 本文の書き換えが台帳を正とした**位置ベース**なので、初回の外部化・撮り直し・中断後の
  再実行がすべて同じべき等な操作になる。

### Negative / Trade-offs
- **リンク切れが無言になる。** ローカルアセットなら欠落はビルドの警告になるが、外部 URL は
  死んでも本文の変換もサイトのビルドも成功する。週次の `asset-health.yml` で見張るが、
  検出は最大 1 週間遅れる。
- **fork や外部コントリビュータが画像を差し替えられない。** アップロードには個人アカウントの
  トークンが要るため、画像の更新はメンテナのアップロード待ちになる（Epic
  [#314](https://github.com/shinyaoguri/metaphor/issues/314) と緊張関係）。コードだけの PR は
  従来どおり出せる。
- **オフラインでは本文の画像が出ない。** 手元で本文を読むとき・dev サーバーで見るときに
  ネットワークが要る。
- 個人アカウントと外部 SaaS への依存が本文にも及ぶ。ただし画像は Probe から再生成できるので、
  最悪でも撮り直して別の置き場へ移せる（URL の一括張り替えで済む）。
- `docs/tutorial/images/` に JSON 2 つだけが残る見た目になる。

### Follow-ups / 残課題
- ~~台帳の `width` / `height` を website 側の remark プラグインで焼き込む~~ **完了**
  （`website/src/plugins/remark-tutorial-image-size.mjs`）。Astro は寸法が分からないと
  毎ビルド全点へプローブのフェッチを飛ばしていた（取得キャッシュとは別経路なので
  `actions/cache` が当たっていても飛ぶ）。焼き込みで消え、キャッシュが温まった状態の
  ビルドは **約 19 秒 → 0.9 秒**になった。副作用としてレイアウトシフトの防止にもなる。
- [#553](https://github.com/shinyaoguri/metaphor/issues/553)（`prefers-reduced-motion`）は
  「`{節}.webp` ↔ `{節}.png` というファイル名の対」で静止画と動きを対応づける前提だった。
  外部化すると URL はハッシュになり、しかも website 側では両方 `.webp` になるため、
  **台帳の `url` / `motion.url` の対**から引く形に変える必要がある。
- 撮り直しのたびに Gyazo 側へ孤児 URL が溜まる（不変・追記型の帰結として受け入れる）。
  棚卸ししたくなったら台帳の git log が全 URL の履歴になっている。
- Examples の画像（359 点・22.8 MiB。リポジトリのメディアの 86%）は手つかず。ゴールデン
  画像・README のサムネイル・Processing 由来の入力データが混ざっており用途が違うので、
  別途切り分ける。
