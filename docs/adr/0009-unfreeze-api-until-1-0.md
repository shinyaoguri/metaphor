# ADR-0009: API 凍結を撤回し、1.0 までは設計の質を優先して破壊的変更を許容する

- **Status**: Accepted
- **Date**: 2026-08-13
- **Deciders**: リポジトリオーナー（本 PR で決定）
- **PR / Commit**: 本 PR

## Context

`v0.9.0`（2026-08-10 リリース）を「API 凍結宣言」として出した。[api-stability-policy.md](../api-stability-policy.md) §9 は `0.9.x` を「freeze rehearsal（凍結リハーサル）」と定め、**additive と fix のみ**、breaking が要るなら「凍結が早すぎた信号」として扱う、としていた。

Issue 棚卸し（2026-08-13）で、この宣言が 3 つの問題を抱えていることが分かった。

### 1. 宿題を残したまま凍結が出た

[v1-release-plan.md](../design/v1-release-plan.md) は「v0.9.0 前に片付ける必要があるもの」として #322 フェーズ 2（命名統一の旧名削除）を挙げていたが、片付かないまま `v0.9.0` が出た（#477）。現在も `@available(*, deprecated)` が **16 箇所**残っている（`beginSVG` / `endSVG` / `beginRecord` / `endRecord` / `endVideoRecord` の旧名系統）。凍結後は削除自体が major を要するため、**1.0 が旧名を抱えたまま凍る**。

### 2. ポリシー内部で同じ操作に 3 つの答えがある

| 節 | 「0.9.x で public API を削除する」の扱い |
|---|---|
| §3 Deprecation | 「Removal happens no earlier than the following minor (**through 0.9.x**)」= 許される |
| §4 変更 → bump の表 | 「Removing, renaming … public API → **major**」= 1.0 まで不可 |
| §9 0.9.x discipline | 「Additive changes and fixes only」= 例外として都度議論 |

#322 はこの 3 つのどれに従うかが決まらず、結果として誰も動かせない状態になっていた。

### 3. 意味論の未決が凍結に間に合わなかった

Processing 互換の振る舞いに未決が残っている — #519（`noFill()` 後の `text()`）・#523（`keyReleased()` で離されたキーが取れない）・#504（矩形版 `text()` の反転）。#523 は本文自身が「API 凍結の前に方針を確定させたい類」と書いているが、確定しないまま凍結が宣言された。

### 凍結が守る対象がまだ育っていない

凍結の価値は**既存利用者の移行コストを守ること**にある。現時点の利用者は実質オーナーのみ（v1.0 昇格のコミュニティ条件「GitHub スター 100 超」に対しスター 1・2026-08-02 時点）。守る対象が薄い一方で、設計の粗さは上記のとおり残っている。凍結の便益と費用が釣り合っていない。

## Considered Options

### (a) 凍結を維持し、宿題は 1.0 の major で片付ける

旧名・非対称な API を 1.0 まで持ち越し、1.0.0 で一気に壊す。preview モジュール宣言（§9）で逃がす道もあるが、上記の宿題は `MetaphorCore` に集中しているため**中核モジュールが preview**になり、凍結宣言の意味が失われる。

### (b) 凍結を維持しつつ、必要なときだけ例外運用する

§9 の「議論のうえで例外」を都度使う。ルールと運用が乖離し、breaking のたびに「これは例外か」を蒸し返す。判断が記録に残らず、次の作業者が同じ議論を繰り返す。

### (c) 凍結を撤回し、1.0 までは breaking を minor で許容する（採用）

SemVer が `0.x` に与えている意味（minor で壊れうる）に運用を戻し、1.0.0 を凍結の起点にする。

## Decision

**`v0.9.0` で宣言した API 凍結を撤回する。1.0.0 に到達するまでは、設計の改善が正当化するなら public API の破壊的変更を minor リリースで入れてよい。**

規律として維持するもの（凍結解除でも捨てない）:

- **deprecation は既定の手順**。無警告削除はしない。`@available(*, deprecated, renamed:)` を公開リリースに 1 度出してから消す（ADR-0005 Amendment の窓）
- ただし **窓を通すこと自体が設計をゆがめる場合は、窓なしの直接変更を許す**（旧名を残すことが API 面を汚す・エイリアスが型推論を曖昧にする等）。その場合は CHANGELOG に移行表と**窓を通さなかった理由**を書く
- **CHANGELOG の `### Breaking Changes` + 移行表**は breaking のたびに必須
- **ランタイム契約**（Probe wire schema / stdin / 契約環境変数）の扱いは変えない。CONTRACT.md のクロスリポ同時 PR 手順が引き続き正
- **描画結果の開示ルール**（ポリシー §5）も変えない

1.0.0 以降は従来どおり — public API の breaking には major を要する。**SemVer の契約は 1.0 から発効する**。

あわせて v1.0 昇格条件を改める:

- 技術条件から「**0.9 系で breaking なしの実績**」を外す。凍結していない期間の無変更実績は、昇格の根拠にならない
- 代わりに「**昇格時点で既知の設計上の宿題が片付いていること**」を条件にする（#322 フェーズ 2、#519 / #523 / #504 の意味論決着など、その時点の open な API 設計課題）
- 「v0.9.0 の入口条件」チェックリストは役目を終える。未消化項目（Phase 2 完了・W4-2 契約フリーズ点 #339）は v1.0 の技術条件へ移す（#477 の決着）

## Consequences

**解ける**

- #322 フェーズ 2（旧名 5 系統の削除）が着手可能になる。minor + `### Breaking Changes` で入る
- #519 / #523 / #504 で「Processing 互換へ寄せる」選択肢が戻る。凍結下では破壊的変更として却下されがちだった側が、設計の良し悪しで選べる
- ポリシー §3 / §4 / §9 の三つ巴が消える。0.9.x の答えは 1 つ（minor + Breaking Changes + 原則 deprecation 窓）

**引き受ける**

- 利用者は `0.9.x` の minor でも壊れうる。README のバージョン記述を「`0.x` なので minor で API が壊れることがある」に戻す。上限ピン（`upToNextMinor`）を案内する
- **1.0.0 の重みが増す**。凍結の運用実績ではなく、宿題の消化で昇格を判断することになるため、昇格判断が「チェックリストが埋まったか」から「設計として納得できるか」に寄る
- 凍結を一度宣言して撤回した事実は残る。`v0.9.0` のリリースノートを書き換えることはせず、本 ADR とポリシーの Status 欄で経緯を追えるようにする

**変わらない**

- preview モジュールの枠組み（§9）は 1.0 昇格時の道具として残す。「1.0 で凍結する対象」と「preview のまま出す対象」を分ける判断は昇格時に必要になる
- `@_exported import`（ADR-0007 Decision 5）・ADR-0003 Amendment の記録既定 OFF は、いずれも「1.0 の確定仕様」としての宣言なので影響を受けない
